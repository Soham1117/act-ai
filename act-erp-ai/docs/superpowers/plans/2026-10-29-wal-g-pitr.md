# WAL-G Point-in-Time Recovery (PITR) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Continuously archive Postgres WAL + base backups to an immutable S3 bucket so a wiped or corrupted Lightsail database can be restored to a chosen second within the last 30 days.

**Architecture:** Keep Postgres on the existing Lightsail Docker Compose stack (`pgvector/pgvector:pg16`). Ship a thin custom image that adds the `wal-g` binary. Postgres `archive_command` pushes every WAL segment to a dedicated backups bucket; a host cron runs `wal-g backup-push` daily and prunes to 30 days. App IAM never touches this bucket. Restore is a documented, scripted drill into a scratch volume — never an automatic overwrite of live data.

**Tech Stack:** PostgreSQL 16, WAL-G (S3), AWS S3 Object Lock (Governance, 30 days), Docker Compose (`infra/docker-compose.prod-lite.yml`), Lightsail instance `ubuntu@3.134.179.142`, region `us-east-2`.

## Global Constraints

- Region: `us-east-2` only (match existing KMS / Lightsail).
- Retention: **30 days** PITR window (base backups + WAL). Change only with an explicit ops decision.
- RPO target: ≤ 60 seconds (`archive_timeout = 60`).
- Backup bucket must be **separate** from the uploads/docs bucket; web app credentials must have **zero** access to it.
- Backup principal: `s3:PutObject` (+ `s3:AbortMultipartUpload`) only for normal ops. Deletes of locked objects must fail. Restore credentials live offline / separate user, used only on restore hosts.
- Do not hook backups to clock-in/out application code.
- Do not replace Lightsail snapshots — keep them as a coarse layer; WAL-G is the DB recovery path.
- Live DB size today ~14 MB; do not over-engineer multi-region replication in v1.
- Existing `infra/scripts/backup-db.sh` stays as an optional weekly logical dump after WAL-G is proven — not a blocker for this plan.
- Never print AWS secrets or DB passwords in logs, plan run output, or git.

- [ ] **Step 1: Create the bucket with Object Lock enabled at creation**

Object Lock cannot be turned on later. Run on an admin workstation / Lightsail with admin AWS creds (not the app role):

```bash
BUCKET=act-persona-db-backups   # change if taken
REGION=us-east-2

aws s3api create-bucket \
  --bucket "$BUCKET" \
  --region "$REGION" \
  --create-bucket-configuration LocationConstraint="$REGION" \
  --object-lock-enabled-for-bucket

aws s3api put-public-access-block --bucket "$BUCKET" \
  --public-access-block-configuration \
  BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true

aws s3api put-bucket-versioning --bucket "$BUCKET" \
  --versioning-configuration Status=Enabled

aws s3api put-object-lock-configuration --bucket "$BUCKET" \
  --object-lock-configuration '{
    "ObjectLockEnabled": "Enabled",
    "Rule": {
      "DefaultRetention": {
        "Mode": "GOVERNANCE",
        "Days": 30
      }
    }
  }'
```

Expected: commands exit 0. `aws s3api get-object-lock-configuration --bucket "$BUCKET"` shows Governance / 30 days.

- [ ] **Step 1: Add Dockerfile**

Create `infra/docker/Dockerfile.postgres-walg`:

```dockerfile
# Postgres 16 + pgvector + wal-g for continuous archive to S3.
FROM pgvector/pgvector:pg16

ARG WALG_VERSION=v3.0.7
ARG TARGETARCH=amd64

USER root
RUN set -eux; \
  apt-get update; \
  apt-get install -y --no-install-recommends ca-certificates curl; \
  curl -fsSL \
    "https://github.com/wal-g/wal-g/releases/download/${WALG_VERSION}/wal-g-pg-ubuntu-20.04-${TARGETARCH}.tar.gz" \
    -o /tmp/wal-g.tgz; \
  tar -xzf /tmp/wal-g.tgz -C /tmp; \
  mv /tmp/wal-g-pg-ubuntu-20.04-${TARGETARCH} /usr/local/bin/wal-g; \
  chmod 755 /usr/local/bin/wal-g; \
  wal-g --version; \
  rm -rf /tmp/wal-g.tgz /var/lib/apt/lists/*

USER postgres
```

Pin `WALG_VERSION` deliberately; bump only after reading release notes.

### Task 3: Cut over Postgres to archive mode + first base backup

**Files:**

- [ ] **Step 1: Write backup-push script**

Create `infra/scripts/walg-backup-push.sh`:

```bash
#!/usr/bin/env bash
# Daily WAL-G base backup + retain 30 days of full backups.
set -euo pipefail
umask 077
export PATH="/home/ubuntu/bin:/usr/local/bin:/usr/bin:/bin:$PATH"

ROOT=/home/ubuntu/act-erp-ai/act-erp-ai
COMPOSE=(docker compose -f "$ROOT/infra/docker-compose.prod-lite.yml")
log() { printf '%s walg-backup: %s\n' "$(date -u +%Y-%m-%dT%H:%M:%SZ)" "$*"; }

cd "$ROOT"
log "backup-push"
"${COMPOSE[@]}" exec -T postgres wal-g backup-push /var/lib/postgresql/data
log "delete retain FULL 30"
"${COMPOSE[@]}" exec -T postgres wal-g delete retain FULL 30 --confirm
log "OK"
```

`chmod +x` on the server after deploy. Note: `wal-g delete` may fail against Object Lock Governance without bypass — if delete fails, document that Object Lock expiry handles retention and make delete best-effort:

```bash
"${COMPOSE[@]}" exec -T postgres wal-g delete retain FULL 30 --confirm || log "WARN: delete skipped (Object Lock or empty history)"
```

### Task 5: Non-destructive restore test (PITR)

**Interfaces:**
- Consumes: restore IAM creds (prompt / env `WALG_RESTORE_ENV_FILE`), target timestamp `RESTORE_TO`
- Produces: exit 0 after verifying row counts on a throwaway data directory; leaves live `pgdata` untouched

- [ ] **Step 1: Write restore-test script**

Create `infra/scripts/walg-restore-test.sh` that:

1. Requires `RESTORE_TO` ISO timestamp (UTC), e.g. `2026-10-29T16:00:00Z`.
2. Creates a temp Docker volume `act-erp-walg-restore-test`.
3. Runs a one-off container from `act-erp-lite-postgres:walg` with restore env, `wal-g backup-fetch` LATEST (or named), writes `recovery.signal` / `restore_command`, sets `recovery_target_time`.
4. Starts Postgres until recovery completes.
5. Runs verification queries (`SELECT count(*) FROM "TimeEntry";`, newest `"AuditLog"."createdAt"`).
6. Tears down the container + volume unless `--keep`.

Core fetch/recovery pattern (embed in the script):

```bash
wal-g backup-fetch /var/lib/postgresql/data LATEST
# then place recovery settings:
# restore_command = 'wal-g wal-fetch %f %p'
# recovery_target_time = '$RESTORE_TO'
# recovery_target_action = 'promote'
touch /var/lib/postgresql/data/recovery.signal
```

Use a **different** volume than `act-erp-lite_pgdata`. Refuse to run if target path equals the live volume name.
